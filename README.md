# Mirage — DPI-устойчивый VPN с decoy-фронтом

Mirage — это протокол и реализация VPN, который:

1. **Шифрует всё.** Транспорт — TLS 1.3 (AES-256-GCM/ECDHE), поверх него идёт
   собственный AEAD-протокол записей с ротацией ключей: ключи выводятся из PSK и
   эфемерного X25519-обмена, параметры обновляются по HKDF.
2. **Неотличим от обычного HTTPS.** Для DPI (в т.ч. ТСПУ) это обычное TLS 1.3
   соединение с SNI легитимного домена. Нет отдельных хендшейков, нет
   сигнатур по размерам пакетов (есть опциональный padding), нет
   характерных таймингов.
3. **Идёт на один сервер, а приходит на другой.** Пакет видимым образом
   направлен на **decoy** (публичный релей), а на самом деле доходит до
   **скрытого VPN-сервера**, адрес которого знает только decoy.

```
                DPI видит только это соединение
                ────────────────────────────────────►
   [ Клиент ]   TLS 1.3, SNI = decoy.example.com    [ Decoy :443 ]
   Windows/                                         публичный IP,
   Linux                                           смотрит в интернет
                                                          │
                                                          │  сырое реле TCP
                                                          ▼
                                                 [ Скрытый VPN-сервер ]
                                                   10.0.0.2:8443
                                                   терминирует TLS,
                                                   аутентифицирует PSK,
                                                   выпускает в интернет
```

## Как достигается устойчивость к DPI

| Техника | Что делает |
| --- | --- |
| Настоящий TLS 1.3 | Внешний слой — не имитация, а реальный `crypto/tls`. Ни один байт не выдаёт протокол. |
| SNI = домен decoy | Даже «правильный» цензор, который подключится к decoy с тем же SNI, получит **байт-в-байт** такой же трафик. |
| Decoy-реле на уровне TCP | Decoy не терминирует TLS: он перекладывает сырые байты в сторону скрытого сервера. Сам decoy не видит plaintextа. |
| Cover-сайт | Любой, кто подключился с другим SNI (сканер, цензор, любопытный), получает обычный HTTPS-сайт. |
| Cover и на скрытом сервере | Не прошедший аутентификацию клиент тоже получает сайт — сервер неотличим от веб-хоста. |
| Пиннинг сертификата | Клиент проверяет SHA-256 сертификата сервера, публичные CA не используются и не могут быть скомпрометированы. |
| AEAD-протокол записей | Тип кадра зашифрован, nonce = base ⊕ sequence (как в TLS 1.3/QUIC), реконструкция ключей по HKDF. |
| Padding (опционально) | `pad_min` дополняет кадры до кратного 16 байтам — глушит размерный анализ. |
| Защита от повторов | Эфемерные ключи кэшируются на время окна; timestamp в хендшейке. |

## Сборка

```sh
cd protocol
go mod tidy          # один раз, нужен интернет для модуля TUN
go build -o mirage ./cmd/mirage
```

Один бинарий содержит все четыре роли. На Windows для режима TUN нужен
**Wintun** — библиотека `golang.zx2c4.com/wireguard/tun` встраивает `wintun.dll`
в бинарий, отдельная загрузка не требуется.

## Проверка без развертывания

Криптоядро и вся цепочка «клиент → decoy → скрытый сервер» покрыты юнит-тестами,
которые работают без сети и без прав root:

```sh
go test ./...
```

Среди них — сквозной тест `internal/relay`: настоящий TLS через decoy, внутренний
хендшейк, обмен кадрами, отход для постороннего SNI на cover-сайт и отказ при
неверном PSK.

## Быстрый старт (всё на одном хосте, для проверки)

```sh
# 1. Материал: CA, сертификат decoy-домена, PSK, статический X25519, конфиги
./mirage keygen -domain decoy.example.com -dir keys

# 2. Скрытый сервер (слушает на localhost:8443)
sudo ./mirage server -c keys/server.json

# 3. Decoy-релей (публичный :443 -> на скрытый сервер)
sudo ./mirage decoy -c keys/decoy.json

# 4. Клиент
sudo ./mirage client -c keys/client.json
```

Клиент поднимет интерфейс `mirage0` с адресом из пула и начнёт гонять IP-пакеты.
В `keys/client.json` поправьте `decoy_addr` на публичный IP/домен decoy.

## Разнесение на два сервера (боевая схема)

1. **Decoy (VPS A)** — публичный IP, домен `decoy.example.com`, `listen: ":443"`,
   `server_addr: "10.0.0.2:8443"` (или приватный адрес второго VPS).
2. **Сервер (VPS B)** — `listen: "10.0.0.2:8443"`, файрвол разрешает вход только
   от IP decoy. NAT в интернет: `deploy/server-nat.sh up`.
3. В идеале между ними — приватная сеть (например, отдельный WireGuard), тогда
   скрытый сервер вообще не торчит в публичный интернет.

Цензор видит только IP(VPS A) и SNI `decoy.example.com`. Чтобы зайти на
настоящий VPN-сервер, нужно скомпрометировать decoy.

## Режимы клиента

* `"mode": "tun"` (по умолчанию) — IP-уровень, виртуальный интерфейс, работает
  для всех приложений сразу. Нужны права администратора/root и драйвер TUN.
* `"mode": "socks"` — локальный SOCKS5-прокси на `socks_listen`, драйверы не
   нужны. Удобно для проверки и для браузера. Мультиплексор соединений
   ходит теми же зашифрованными кадрами.

## Маршрутизация и DNS

* `routes` — список CIDR, которые уйдут в туннель.
* `default_route: true` — весь трафик через туннель. При этом автоматически
  добавляется хост-маршрут на decoy через прежний шлюз, чтобы туннель не
  ушел сам в себя.
* На Linux `dns_via_tunnel: true` допишет `nameserver` в `/etc/resolv.conf`
  (best effort, бэкап восстанавливается при выходе). На Windows DNS
  прописывается через `netsh`.
* На сервере поднимается встроенный DNS-релей (`dns_listen` → `dns_upstream`),
  так что запросы идут через туннель и не утекают наружу.

## NAT на скрытом сервере

```sh
sudo deploy/server-nat.sh up      # включает форвардинг и MASQUERADE
sudo deploy/server-nat.sh down    # отключает
```

Systemd-юниты в `deploy/` вызывают этот скрипт автоматически.

## Дополнительная скрытность

1. **Настоящий сертификат на decoy-домен.** Сертификат из `keygen` — от
   внутреннего CA (и пиннинг это допускает). Если получить настоящий
   сертификат для `decoy.example.com` (например, ACME через DNS-01) и указать
   его в `tls_cert`/`tls_key` сервера и в `cover_cert`/`cover_key` decoy, то
   активное пробирование с тем же SNI даст валидный для браузера сайт.
2. **Cover-сайт как зеркало.** `cover_proxy` на decoy может реверс-проксировать
   на ваш настоящий сайт — и туннель, и сайт будут отвечать одинаково.
3. **Padding.** `"pad_min": 64` — выровнять маленькие пакеты (ACK и т.п.).
   Чуть больше трафика, но ровные размеры кадров.
4. **Не светите сервер.** `server_addr` decoy должен быть приватным/скрытым;
   ограничьте порт 8443 файрволом до IP decoy.

## Модель безопасности

* Внешний TLS 1.3 даёт конфиденциальность, целостность и forward secrecy на
  транспорте.
* Внутренний хендшейк (PSK + эфемерный X25519) аутентифицирует клиента
  перед сервером и наоборот (ключевое подтверждение через Welcome), а также
  защищает полезную нагрузку, если TLS вдруг окажется скомпрометированным
  (например, MITM-боксом с доверенным CA — у нас пиннинг, поэтому это
  исключено).
* Decoy — тупое TCP-реле: он не имеет ключей и не видит plaintextа ни на
  одном из слоёв.
* Replay-атаки на хендшейк отбиваются кэшем эфемерных ключей и окном
  timestamp (±5 минут).
* PSK — главный секрет. Кто знает PSK, тот может пользоваться VPN; храните
  `psk.txt` и `client.json` в секрете.

## Известные ограничения

* Внешний транспорт — TCP («TCP-in-TCP»): ценой скрытности является
  некоторая просадка скорости на.bulk-трафике. Для интерактива незаметно.
* IPv6-маршруты на Windows-клиенте не настраиваются (только IPv4); пакеты
  IPv6 через туннель ходят, если интерфейсу выдан v6-адрес.
* Драйвер Wintun на Windows-клиенте загружается из встроенного в бинарь
  ресурса; прав администратора для настройки интерфейса обязательны.
* Пул адресов сервера — на одну /24 по умолчанию; меняйте `tunnel_cidr` и
  `ip_start`/`ip_end` для больших сетей.
* `default_route` на Windows меняет таблицу маршрутов; при аварии туннеля
  маршруты снимаются при корректном выходе (Ctrl+C), но при жёстком kill —
  останутся. Команда `route delete` в скрипте `deploy/win-cleanup.txt`.

## Структура проекта

```
cmd/mirage            бинарий: keygen | client | server | decoy
internal/proto        константы протокола
internal/hkdf         HKDF-SHA256 (без внешних зависимостей)
internal/record       AEAD-кадры, реконструкция ключей, padding
internal/handshake    внутренний хендшейк PSK+X25519
internal/tlscam       TLS 1.3 конфиги, пиннинг, сниффер SNI
internal/tunmgr       TUN (Wintun / /dev/net/tun / utun), адреса, маршруты
internal/session      насос клиентской и серверной сессий
internal/mux          мультиплексор TCP для SOCKS-режима
internal/socks        SOCKS5-сервер
internal/dns          встроенный DNS-релей
internal/cover        cover-сайт для проб и посторонних
internal/relay        decoy: снифф SNI -> реле или сайт
internal/server       скрытый сервер: пул IP, таблица сессий, TUN-роутинг
internal/client       клиент с автореконнектом
internal/certs        генерация CA и сертификатов
internal/conf         JSON-конфиги всех ролей
deploy                NAT-скрипт и systemd-юниты
examples              примеры конфигов
```
