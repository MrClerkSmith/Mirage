# Mirage — DPI-устойчивый VPN за TLS 1.3-фасадом

Mirage — это протокол и реализация VPN, который:

1. **Шифрует всё.** Транспорт — TLS 1.3 (AES-256-GCM/ECDHE), поверх него идёт
   собственный AEAD-протокол записей с ротацией ключей: ключи выводятся из PSK и
   эфемерного X25519-обмена, параметры обновляются по HKDF.
2. **Неотличим от обычного HTTPS.** Для DPI (в т.ч. ТСПУ) это обычное TLS 1.3
   соединение с SNI легитимного домена. Нет отдельных хендшейков, нет
   сигнатур по размерам пакетов (есть опциональный padding), нет
   характерных таймингов.
3. **Один сервер — и туннель, и сайт.** На соединение с нужным SNI сервер
   отвечает туннелем (после внутренней аутентификации), а на любое другое —
   обычным HTTPS-сайтом. Адрес VPN-сервера виден в сертификате так же, как у
   любого хостинга.

```
                DPI видит только это соединение
                ────────────────────────────────────►
   [ Клиент ]   TLS 1.3, SNI = example.com         [ Сервер :443 ]
   Windows/                                        публичный IP,
   Linux                                           смотрит в интернет
                                                         │
                              не прошёл PSK-хендшейк ────┼──── прошел ──┐
                                    ▼                                   ▼
                          cover-сайт (обычный HTTPS)          TUN → NAT → интернет
```

## Как достигается устойчивость к DPI

| Техника | Что делает |
| --- | --- |
| Настоящий TLS 1.3 | Внешний слой — не имитация, а реальный `crypto/tls`. Ни один байт не выдаёт протокол. |
| Cover-сайт | Любой, кто подключился с другим SNI или без правильного PSK (сканер, цензор, любопытный), получает обычный HTTPS-сайт. |
| Пиннинг сертификата | Клиент проверяет SHA-256 сертификата сервера, публичные CA не используются и не могут быть скомпрометированы. |
| AEAD-протокол записей | Тип кадра зашифрован, nonce = base ⊕ sequence (как в TLS 1.3/QUIC), реконструкция ключей по HKDF. |
| Padding (опционально) | `pad_min` дополняет кадры как минимум до N байт (с округлением вверх кратно 16) — глушит размерный анализ. |
| Защита от повторов | Эфемерные ключи кэшируются на время окна; timestamp в хендшейке. |

## Сборка

```sh
git clone https://github.com/MrClerkSmith/Mirage.git
cd Mirage
go mod tidy          # один раз, нужен интернет для модуля TUN
go build -o mirage ./cmd/mirage
go build -o mirage-admin ./cmd/mirage-admin
```

Два бинария: `mirage` — все роли (keygen/client/server), `mirage-admin` —
управление сервером. На Windows для режима TUN нужен **Wintun** — библиотека
`golang.zx2c4.com/wireguard/tun` встраивает `wintun.dll` в бинарь, отдельная
загрузка не требуется.

## Проверка без развертывания

Криптоядро покрыто юнит-тестами, которые работают без сети и без прав root:

```sh
go test ./...
```

Среди них — векторы RFC 5869 для HKDF, раунды AEAD-записей (ротация ключей,
уникальность nonce, подмена байтов) и формат контрольных сообщений.

## Быстрый старт

```sh
# 1. Материал: внутренний CA, сертификат домена, PSK, статический X25519, конфиги
./mirage keygen -domain example.com -dir keys

# 2. Сервер (публичный :443 → туннель + cover-сайт)
sudo ./mirage server -c keys/server.json

# 3. Клиент
sudo ./mirage client -c keys/client.json
```

Клиент поднимет интерфейс `mirage0` с адресом из пула и начнёт гонять IP-пакеты.
В `keys/client.json` поправьте `server_addr` на публичный IP/домен сервера.

Чтобы клиенты вышли в интернет, на сервере нужен NAT:

```sh
sudo deploy/server-nat.sh up      # форвардинг + MASQUERADE + clamp MSS
sudo deploy/server-nat.sh down    # отключить
```

Systemd-юнит `deploy/mirage-server.service` вызывает этот скрипт автоматически.

## Развёртывание одной командой

На Linux-сервере всё ставится автоматически — скрипт сам определит дистрибутив,
обновит систему, поставит Go, склонирует репозиторий, соберёт бинари и
поставит systemd-сервис:

```sh
curl -fsSL https://raw.githubusercontent.com/MrClerkSmith/Mirage/main/deploy/install.sh | sudo sh
```

Что он делает: `apt`/`dnf`/`pacman`/`apk` → обновление и установка git, curl,
iptables; официальный тарбол Go, если системного Go нет или он старше 1.23;
сборка `/usr/local/bin/mirage` и `/usr/local/bin/mirage-admin`; ключи и
конфиги в `/etc/mirage`; открытие 443/tcp в firewall; включение сервиса
`mirage-server`. В конце спросит домен и публичный адрес и запустит keygen.

## Управление: TUI

Клиентов и входящие конечные точки (inbound) удобно создавать через терминальный
интерфейс:

```sh
sudo mirage-admin -c /etc/mirage/server.json
```

```
Mirage admin
config: /etc/mirage/server.json

Main menu
> Clients (1)
  Inbounds (1)
  Save & exit
  Quit without saving

↑↓ move · enter open · q quit
```

* **Clients** — список PSK-записей: `a` создать клиента (генерит PSK),
  `d` удалить, `e` выгрузить готовый `clients/<id>.json` для выбранного inbound.
* **Inbounds** — список слушателей: `a` добавить (id, домен, адрес, транспорт —
  сертификат для домена генерируется автоматически), `d` удалить. Каждый inbound
  — это отдельный порт/домен/транспорт с собственным сертификатом, ведущий в тот
  же туннель; удобно разнести клиентов по разным SNI.

Изменения пишутся на диск только через «Save & exit». Если `server.json` ещё не
существует, TUI спросит хост и домен и создаст всё с нуля.

## Подключение клиента с компьютера

1. На сервере создайте клиента и выгрузите его конфиг (см. раздел выше) —
   получится `/etc/mirage/clients/home.json` с уже прописанными `server_addr`,
   пиннингом сертификата и ключами. Перенесите файл на компьютер.
2. Соберите клиент (см. «Сборка») или скопируйте готовый бинарий.
3. Запустите от **администратора** — Wintun требует прав на создание интерфейса:

```sh
mirage.exe client -c home.json
```

Появится интерфейс `mirage0`, и весь трафик приложений пойдёт через туннель.
Без прав администратора работает режим SOCKS: поставьте в копии конфига
`"mode": "socks"` и укажите в браузере `socks5://127.0.0.1:1080`.

Проверка: `ping 10.7.0.1` отвечает серверу туннеля, а любой IP-чекер
покажет адрес сервера, а не ваш.

## Режимы клиента

* `"mode": "tun"` (по умолчанию) — IP-уровень, виртуальный интерфейс, работает
  для всех приложений сразу. Нужны права администратора/root и драйвер TUN.
* `"mode": "socks"` — локальный SOCKS5-прокси на `socks_listen`, драйверы не
  нужны. Удобно для проверки и для браузера. Мультиплексор соединений
  ходит теми же зашифрованными кадрами.

## Внешний транспорт и SNI

Туннель можно нести тремя способами — выбор меняет только то, как соединение
выглядит для наблюдателя. Внутри всегда один и тот же зашифрованный протокол.

| Транспорт | Как выглядит | Зачем |
| --- | --- | --- |
| `raw` | обычный HTTPS к домену | по умолчанию, минимум накладных |
| `ws` | WebSocket (wss) к домену | работает за nginx/CDN, легко blend'ится |
| `grpc` | gRPC-вызов к API-домену | трафик RPC-сервиса, правдоподобно для API-SNI |

Транспорт задаётся в конфиге сервера (в каждом `inbounds` — поле `transport`) и
клиента (`transport`), путь для ws/grpc — поле `path` (по умолчанию `/mirage`).
Любой inbound обслуживает один и тот же туннель, так что клиентов можно
разнести по разным портам/SNI/транспортам.

Переопределить на лету, без правки конфига:

```sh
./mirage client -c client.json -sni other.example.com -transport ws
```

`-sni` подменяет SNI в ClientHello и Host в HTTP-заголовках (сертификат
продолжает проверяться по пиннингу SHA-256, так что работает и для домена,
отличного от того, что в конфиге).

**Про xhttp:** это специфичный транспорт Xray (splitting по HTTP-запросам),
который имеет смысл только вместе с VLESS/VMess-клиентами. Mirage говорит на
своём протоколе, поэтому `ws` и `grpc` закрывают те же задачи маскировки —
первый даёт проход через CDN, второй маскирует трафик под API.

## Маршрутизация и DNS

* `routes` — список CIDR, которые уйдут в туннель.
* `default_route: true` — весь трафик через туннель. При этом автоматически
  добавляется хост-маршрут на сервер через прежний шлюз, чтобы туннель не
  ушёл сам в себя.
* На Linux `dns_via_tunnel: true` допишет `nameserver` в `/etc/resolv.conf`
  (best effort, бэкап восстанавливается при выходе). На Windows DNS
  прописывается через `netsh`.
* На сервере поднимается встроенный DNS-релей (`dns_listen` → `dns_upstream`),
  так что запросы идут через туннель и не утекают наружу.

## Дополнительная скрытность

1. **Настоящий сертификат на домен.** Сертификат из `keygen` — от внутреннего CA
   (и пиннинг это допускает). Если получить настоящий сертификат для
   `example.com` (например, ACME через DNS-01) и указать его в
   `tls_cert`/`tls_key` нужного inbound сервера, то активное пробирование с тем
   же SNI даст валидный для браузера сайт.
2. **Cover-сайт как зеркало.** `cover_proxy` конкретного inbound может
   реверс-проксировать на ваш настоящий сайт — и туннель, и сайт будут
   отвечать одинаково.
3. **Padding.** `"pad_min": 64` — выровнять маленькие пакеты (ACK и т.п.).
   Чуть больше трафика, но ровные размеры кадров.

## Модель безопасности

* Внешний TLS 1.3 даёт конфиденциальность, целостность и forward secrecy на
  транспорте.
* Внутренний хендшейк (PSK + эфемерный X25519) аутентифицирует клиента
  перед сервером и наоборот (ключевое подтверждение через Welcome), а также
  защищает полезную нагрузку, если внезапно окажется скомпрометированным
  внешний TLS — сертификат всё равно проверяется пиннингом, а не цепочкой CA.
* Replay-атаки на хендшейк отбиваются кэшем эфемерных ключей и окном
  timestamp (±5 минут).
* PSK — главный секрет. Кто знает PSK, тот может пользоваться VPN; храните
  `psk.txt` и `client.json` в секрете.

## Известные ограничения

* Внешний транспорт — TCP («TCP-in-TCP»): ценой скрытности является
  некоторая просадка скорости на bulk-трафике. Для интерактива незаметно.
  Для `grpc` добавляется ещё потоковое управление HTTP/2 (окно 64 КБ на
  поток), так что большие передачи на нём самые медленные; держите
  `idle_ping_sec` ниже 5 минут, чтобы соединение не закрывалось по таймауту.
* IPv6-маршруты на Windows-клиенте не настраиваются (только IPv4); пакеты
  IPv6 через туннель ходят, если интерфейсу выдан v6-адрес.
* Драйвер Wintun на Windows-клиенте загружается из встроенного в бинарь
  ресурса; прав администратора для настройки интерфейса обязательны.
* Пул адресов сервера — на одну /24 по умолчанию; меняйте `tunnel_cidr` и
  `ip_start`/`ip_end` для больших сетей.
* `default_route` на Windows меняет таблицу маршрутов; при аварии туннеля
  маршруты снимаются при корректном выходе (Ctrl+C), но при жёстком kill —
  останутся. Команда `route delete` в скрипте `deploy/win-cleanup.txt`.

## Структура проекта

```
cmd/mirage            бинарий: keygen | client | server
cmd/mirage-admin      терминальный интерфейс управления сервером
internal/proto        константы протокола
internal/hkdf         HKDF-SHA256 (без внешних зависимостей)
internal/record       AEAD-кадры, реконструкция ключей, padding
internal/handshake    внутренний хендшейк PSK+X25519
internal/tlscam       TLS 1.3 конфиги и пиннинг сертификата
internal/tunmgr       TUN (Wintun / /dev/net/tun / utun), адреса, маршруты
internal/session      насос клиентской и серверной сессий
internal/transport    внешний транспорт: raw / ws / grpc
internal/mux          мультиплексор TCP для SOCKS-режима
internal/socks        SOCKS5-сервер
internal/dns          встроенный DNS-релей
internal/cover        cover-сайт для проб и посторонних
internal/server       сервер: пул IP, таблица сессий, TUN-роутинг
internal/admin        хранилище конфига + TUI (клиенты и inbound)
internal/client       клиент с автореконнектом
internal/certs        генерация CA и сертификатов
internal/conf         JSON-конфиги обеих ролей
deploy                install.sh, NAT-скрипт и systemd-юнит
examples              примеры конфигов
```
